Text2Prod guide

Chapter 10

Recipes and pitfalls

Ten prompts to copy, each tied to the chapter that explains it, and six mistakes to skip.

Recipes

Restate a noisy report first

/text2prod:zed-mode read this issue thread and restate the real problem in plain words. don't touch code yet.

A misreading shows up in the restatement, where one reply corrects it, instead of in a diff you have to discard. Read chapter 3 for the full workflow.

Fix a bug with proof

/text2prod:zed-mode use the bug-fix playbook. the nightly export skips the last page of results. reproduce it first, then fix it. done means the three-page fixture exports every row. show me the counts before and after.

Naming the playbook gets you its steps, and reproducing first gives the fix a test that failed before it passed. The done check can fail, and the before and after counts are the proof. See chapter 5.

Ask a read-only question

/text2prod:zed-mode use the investigation playbook. how does a session pick up the bootstrap on OpenCode? read-only. cite file paths for every claim.

The investigation playbook makes no edits and opens no PR, and the demand for file paths makes each claim checkable. See chapter 3.

Add a small feature

/text2prod:zed-mode use the feature playbook. add a --dry-run flag to the bump script. it prints what would change and writes nothing. tests first.

The prompt states the behavior in one sentence, including what must not happen, and "tests first" sets the order of work. See chapter 5.

Prototype before you pick

/text2prod:zed-mode use the prototype playbook. prototype two layouts for the settings page behind a toggle and send me a screenshot of each before we pick.

You choose between two things you can see instead of two descriptions. The prototype stays throwaway, and the real build follows through the feature playbook. See chapter 4.

Plan a settled design

/text2prod:zed-mode turn the approved spec into a plan of small tasks, each with its own test.

Use it after you approve the spec. Small tasks that each carry a test give every step of the build a check. See chapter 4.

Review a branch skeptically

/text2prod:zed-mode interrogate this branch. read-only. report only real bugs or behavior regressions.

At least two reviewers attack the change from different angles, and the lead checks every finding against the code. Limiting the report to real bugs and regressions keeps style opinions out of it. The skill never applies a change, so you decide what to act on. See chapter 4.

Get a PR green

/text2prod:zed-mode use the babysit playbook. check on PR 42 and get it green. don't force-push.

Babysit works conflicts, then review threads, then CI, and stops when the PR is merge-ready. It never merges, and the prompt repeats its no-force-push limit. See chapter 6.

Vet a number

/text2prod:zed-mode did the cache change make startup faster? measure ten runs before and after and explain the number before you report it.

The run count clears the benchmark checklist's floor, and the request to explain the number sends the agent looking for the limiter. See chapter 6.

Run overnight

/text2prod:zed-mode use the autonomous-run playbook. going to bed. finish the remaining plan tasks, log each decision, and stop before anything irreversible.

The exit condition is the end of the plan, each decision lands in a log you can read in the morning, and irreversible actions still pause. See chapter 7.

Pitfalls

Listing skills instead of stating the goal

The bootstrap checks for a matching skill before it replies and starts with the process skills that set the approach. A list of skills you typed overrides that judgment, and the agent may run one the work did not need. State the goal and the done check, and name a playbook only when you want its steps. Chapter 2 covers the five parts of a good prompt.

A done check that cannot fail

"Make it better" gives the agent nothing to verify, so it declares victory whenever it stops. Write a check with a yes or no answer, such as "the three-page fixture exports every row". Chapter 6 explains why the agent has to run the check before it says done.

Leading with your theory of the cause

A theory narrows the search to the place you pointed at, and if you are wrong, the agent spends its time confirming the wrong spot. Give the symptom, when it started, and what you already ruled out. The systematic-debugging skill traces the cause before it proposes a fix. See chapter 3.

Treating one approval as approval for everything after it

Each stage needs its own yes. Approving an idea does not approve a spec that does not exist yet, and approving a plan does not approve a merge. Say yes to the stage in front of you, and expect the agent to ask again at the next gate. See chapter 4.

Accepting "should work"

"Should", "probably", and "seems to" are the words of a claim nobody checked. Ask for the command output, the screenshot, or the number, and for the level of evidence behind it. See chapter 6.

Granting autonomy without a stop line

"Don't stop" with no exit condition gives the agent nothing to finish toward. Name the condition that ends the run, such as tests green or all plan tasks verified, and name what must pause, such as a merge or a deploy. See chapter 7.
