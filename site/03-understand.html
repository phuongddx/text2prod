Chapter 3

Understand before editing

Read first, then change. A read-only pass costs one message. A wrong fix costs a review cycle and a revert. This chapter covers the playbooks and the skill that keep the agent reading until it knows the cause.

Ask a read-only question

The investigation playbook is for questions such as how something works, why it was built that way, or whether a claim holds. The agent reads the affected code and its docs. For a "why" question it also reads git log and git blame and any linked issues. It cites file paths and commits.

The answer comes as Overview, Key concepts, How it works, Where things live, and Gotchas. For a choice between alternatives, it gives a recommendation with a trade-offs table. If the question needs a probe to answer, such as a timing or an output, it runs the brainstorming spike path and reports what it observed.

/text2prod:zed-mode use the investigation playbook. how does a session pick up the bootstrap on OpenCode? read-only. cite file paths for every claim.

The playbook makes no edits and opens no PR. If the answer leads to a code change, it hands back to you, and the change goes through the bug-fix or feature playbook.

Restate a noisy report first

Issue threads mix symptoms, guesses, and old workarounds. Ask the agent to say what the real problem is before it touches anything.

/text2prod:zed-mode read this issue thread and restate the real problem in plain words. don't touch code yet.

A misreading shows up in the restatement, while you can still correct it in one reply. After code exists, the same misreading is a diff you have to review and discard. The brainstorming skill builds in the same step: it writes back its understanding of the outcome and constraints and asks you to correct it before it designs anything.

Debug to the root cause

The systematic-debugging skill has one rule: no fixes without root cause investigation first. Until phase 1 is done, the agent proposes no fix. The skill applies to any bug, test failure, or unexpected behavior, and it says to use it most when you are under time pressure or the cause seems obvious.

PhaseWhat the agent does
1. Root cause investigationReads the error and stack trace in full, reproduces the failure, checks recent changes, adds logging at each component boundary to find where it breaks, and traces the bad value back to its source.
2. Pattern analysisFinds similar code that works and lists every difference from the broken code.
3. Hypothesis and testingStates one hypothesis, makes the smallest change that tests it, and changes one variable at a time.
4. ImplementationWrites a failing test, makes a single fix for the root cause, and verifies it.

After three failed fixes the agent stops and questions the architecture. It does not try a fourth fix without discussing it with you.

Symptoms and captured traces

Two playbooks diagnose without fixing. Both end with a cited diagnosis, and neither changes code unless you ask. Once the cause is known, the work goes to bug-fix or perf-issue.

PlaybookUse it whenWhat the agent does
runtime-forensicsThe symptom is live: a leak, a spin, or a glitch in a running process.Captures a real signal (a CPU profile for a spin, a heap snapshot for a leak, a devtools trace for a glitch), reduces it to the hot path or retainer chain, proves the mechanism by injecting instrumentation into the running process, and maps it to a file, symbol, and line.
trace-forensicsThe capture already exists: a profile, trace, spindump, or heap snapshot you hand over.Identifies the format, loads it into something queryable, narrows to the cause, and attributes it to source through the artifact's own symbols. Without a paired before-and-after capture, it labels the finding a hypothesis, not a confirmed cause.
