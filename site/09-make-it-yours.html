Make it yours

Fit Text2Prod to a repository and a team, then test a skill change before it ships. This chapter covers onboarding a repo, team templates, writing a skill, and running an eval on an edit.

Onboard a repository

/text2prod:zed-mode onboard this repo for AI-native work.

This runs the init-project skill. It works in phases and writes nothing until its research is done.

  • Gates first, read-only. If AGENTS.md already exists, the agent skips that step, does not read the file as input, and reports it unchanged. If .agents/ or ARCHITECTURE.md exists, it creates only the missing pieces.
  • Research, read-only. Four passes cover the core source, the tests, the configs and build, and the scripts, docs, and git history. They run as parallel agents when the harness can delegate, and inline otherwise. The skill never invents a command. Anything absent is written as Not configured.
  • Generation, for missing pieces only. A root AGENTS.md titled Repository Guidelines, a thin ARCHITECTURE.md, and docs/engineering/ with conventions.md, infrastructure.md, and tech-stack.md. The starter structure adds .agents/skills/, .agents/policies/, .agents/hooks/, .agents/templates/spec.md, .agents/templates/review.md, and docs/features/.
  • Report. A table marks every target path as created, skipped, or pre-existing, and the agent recommends committing the structure as its own commit before feature work.

The skill never modifies an existing AGENTS.md, CLAUDE.md, or GEMINI.md, and it never creates src/ or tests/. You do not have to ask for onboarding. When you start feature work in a repo that has neither .agents/ nor ARCHITECTURE.md, the agent offers the starter structure once per task. A "no" is final, and the task goes ahead either way.

Team templates

The agent resolves spec.md and review.md from the first of these that exists.

  1. .agents/templates/<name>.md in your repository, the team's own version.
  2. The template bundled with the zed-mode skill.
  3. The owning skill's built-in format.

Onboarding copies the bundled templates into .agents/templates/, so editing those two files changes every future spec and review in the repo. plan.md has no template, because writing-plans defines its format. Before it designs anything, brainstorming reads AGENTS.md or CLAUDE.md, then ARCHITECTURE.md, docs/engineering/*.md, and .agents/policies/*, so rules you put there shape the design.

Write or change a skill

A skill shapes behavior, so the writing-skills skill treats writing one as test-driven development applied to process documentation. The failing test is a pressure scenario run with a subagent and no skill, and the agent's baseline behavior is what you watch fail. You write the skill to address those specific failures, run the scenario again to see the agent comply, and then close any loopholes you find.

One rule in that skill is easy to miss. A skill's description begins with "Use when" and states only the triggering conditions. A description that summarizes the workflow gives the agent a shortcut, and it may follow the summary instead of reading the skill.

The authoring-a-skill playbook wraps this in four steps.

  1. Follow writing-skills.
  2. Validate the skill. The frontmatter has a name and a description that starts "Use when", the files it references exist, and its links to other skills resolve.
  3. Prove the behavior change with the eval playbook. A structural change also gets a static test under tests/.
  4. Open the PR with opening-a-pr.

The playbook's guidance on length is short: when in doubt, delete, and keep only prose that changes a decision.

Test the change before promoting it

The eval playbook is for any change to a skill, playbook, or prompt that shapes agent behavior. For a Text2Prod skill or playbook, the runner is a plugin-evals/<case>/ folder. It holds a prompt.md and one or more files under graders/, and it runs with claude plugin eval . --eval-dir plugin-evals --case <case>. The agent runs the case on the unedited plugin first and records that result. Only then does it run the case with your edit, so a pass rate always has a baseline next to it.

The playbook prefers deterministic graders, tool_used, regex, and file_exists, over an llm grader. The prompt the candidate sees reads like an ordinary user request. It avoids words such as eval, test, judge, and score, and it never asks the candidate which skills it used. Chain-following is graded from the session transcript, not from the candidate's own account.

Before the agent reports a pass rate, it applies Explain the Number from chapter 6, Verify and ship. Text2Prod's own testing notes, docs/testing.md, add one more step: when a pass count decides whether a change ships, rerun once with --keep-temp and read the matched lines in the traces.

/text2prod:zed-mode use the eval playbook to check my edit to the brainstorming skill before I merge it.
