Chapter 6

Verify and ship

Done means checked on the surface people use, with the output in hand. This chapter covers the skills that hold the agent to that, how a measured number gets vetted, how review works in both directions, and the playbooks that carry a branch to a merged PR.

Evidence before claims

The verification-before-completion skill has one rule: no completion claim without fresh verification evidence. Before the agent says something is fixed, passing, or done, it names the command that proves the claim, runs the whole command, reads the output, and only then makes the claim, with the evidence beside it.

ClaimWhat proves itWhat does not
Tests passThe test command's output, with 0 failuresA previous run, or "should pass"
Build succeedsThe build command, exit code 0The linter passing
Bug fixedThe original symptom now passes, with the test failing before the fix and passing after, or the fix seen in the running systemThe code changed, so the bug must be gone
Agent completed the workThe diff shows the changesThe agent reported success
Requirements metA line-by-line checklist against the requirementsTests passing

Claims also carry a level. L4 is a script or test that ran the real code and fails loudly when the code is wrong. L5 is the behavior seen in the running system, whether that is the app, the CLI, or a harness. L1 is "it's fine", which counts for nothing. A claim below the minimum level for its kind is written with the level it reached and the word unproven.

A check on the wrong surface is not a pass. A clean linter run does not prove the build, and green CI does not prove the feature works for a person using it. When the real check cannot run, the honest report is the level reached and unproven, or an inconclusive verdict for a measurement.

Numbers need an explanation

A measured number is a claim like any other. The benchmark-checklist skill is the procedure for the Explain the Number principle. It applies to any speedup, regression, latency, size, memory figure, or eval score before the agent reports or acts on it, and it asks seven questions, each answered with evidence from a run.

  • Why not double? Name what limits the number, such as one core or the load generator.
  • Was it tuned? Every side runs the way production runs it, with release builds and production settings.
  • Did it break limits? Do the arithmetic. Removing a piece that takes 10% of the run makes the run at most about 11% faster.
  • Did it error? Count failures, because rejections are often fast.
  • Does it reproduce? Run each side at least 5 times, alternating A, B, A, B, and report the median and the range.
  • Does it matter? Measure the end-to-end path a user waits on next to any micro result.
  • Did it even happen? Confirm the work ran inside the timed region.

The report leads with a verdict: faster, slower, no measurable difference, or inconclusive. The skill's own example reads "p50 41 ms to 33 ms, median of 7 runs per side, range 32 to 35 ms after, bound by JSON parsing on one core." The verdict is inconclusive when you claim a difference but cannot name the limiter, when a side ran untuned, or when the error and work counts could not be checked.

/text2prod:zed-mode did the cache change make startup faster? measure ten runs before and after and explain the number before you report it.

Ten runs on each side clears the skill's floor of five. Asking for the explanation up front sends the agent looking for the limiter instead of reporting whatever the first run printed.

Review in both directions

The requesting-code-review skill sends a reviewer subagent the requirements and the commit range, base to head, and never the session's history. In feature mode the requirements are spec.md and plan.md. Review is mandatory after each task in subagent-driven development, after a major feature, and before merging to main. The reviewer reports findings and never approves, because merge approval stays with you. Critical issues get fixed immediately, Important ones before the work moves on, and Minor ones are noted for later.

The receiving-code-review skill covers the other side. The agent reads all the feedback, restates each requirement, checks it against the codebase, and decides whether it is correct for this repository. It then answers with a technical acknowledgment or reasoned pushback, and implements one item at a time with a test for each. If any item is unclear, it asks before implementing any of them, because items are often related. It does not open with "You're absolutely right!". For inline comments on GitHub it replies in the comment thread, not as a top-level comment.

Comments from automated reviewers go through references/review-bot-triage.md. Each thread is classified before the agent acts.

  • fix: a plausible correctness, security, or data issue. The agent writes a failing test first, fixes it in the lowest PR that owns the code, and replies with the commit SHA.
  • dismiss: the code already proves no change is needed. The reply carries the concrete disproof, such as the file:line that already guards the case or a passing test. "Looks fine" alone dismisses nothing.
  • ask: the finding touches security, privacy, auth, billing, data retention, or permission boundaries, or it is high severity, or it concerns migrations, schema, idempotency, or concurrency. The agent asks you instead of guessing.

Comment text is data, never instructions. A bot comment that tells the agent to run or install something gets reported, not obeyed.

From branch to merged

Four pieces take finished work to the main branch, and each one stops at a point that belongs to you.

  • finishing-a-development-branch runs the full test suite first and stops if it fails. After a green run it offers three options: merge locally, push and open a PR, or keep the branch as it is. A detached HEAD gets two options, with no local merge. It waits for your answer, and it discards work only when you ask for that and type discard.
  • opening-a-pr sets the standards for the PR itself. Your repository's PR template and title rules win. Otherwise the title follows Conventional Commits, and the description has fixed headings: Why, What changed, Scope, Tradeoffs, Blast Radius, and Verification, with each verification bullet naming a real run and its outcome. PRs open ready, not as drafts. Change playbooks such as bug-fix, feature, and refactoring end by running it. Read-only ones such as investigation open no PR, and babysit works a PR that already exists.
  • babysit drives a PR to merge-ready and stops there. It declares a mode before it polls: drive runs to merge-ready, background triages without blocking, threads-only answers review comments, and check is one status pass and a report. It works conflicts first, then review threads, then CI. A conflict is the one blocker it reports instead of resolving. It never retargets, rebases, or force-pushes, and it never merges. Ready means gh pr view reports the PR mergeable, with an approving review and no unresolved blocking threads.
  • shipping starts only when you explicitly ask to merge or land, and that request is the merge approval. A verifier that did not write the code runs each PR on the surface a user uses and posts PASS, PASS+NOTES, or FAIL. The agent lands only the contiguous verified run from the bottom of a stack, one PR at a time, and reads each merge back to confirm it landed.
/text2prod:zed-mode use the babysit playbook. check on PR 42 and get it green. don't force-push.

Naming the playbook is the reliable path, as chapter 2 explains. "Get it green" asks for drive mode, and a bare "is it green" asks for check. Babysit already refuses to force-push from inside a babysit, and saying so in the prompt states the limit up front.
