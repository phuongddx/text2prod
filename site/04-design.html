Chapter 4

Design the change

The design settles before the code starts, and the size of the change decides how much design it gets. The brainstorming skill sorts every request into one of three paths and holds the agent at an approval gate on each.

Spike, bounded, or architectural

The agent classifies the request out loud before its first question, so you can override the call. When it is unsure between two paths, it takes the heavier one. If hidden complexity shows up mid-task, it stops, says so, and steps up to the heavier path. A task never moves down a path.

PathWhat it isWhat you approveWhat it leaves behind
SpikeA feasibility question: "can we...", "is it possible...". The output is an answer, not code you keep.The question and the probe, in two or three sentences. A nod is enough.A recommendation. Anything the agent built is labeled throwaway.
BoundedA well-scoped change to a flow that already exists in the repo, such as a new flag or a small endpoint.A short design in chat.The change itself. No spec file and no plan document.
ArchitecturalA new project, a new subsystem, or a change to an interface other code depends on.The design in sections, then the written spec, then the written plan and how to execute it.spec.md and plan.md, then the implementation.

  Q["Request"] --> C{"Classify"}
  C -->|Can we...?| S["Spike"]
  C -->|Small change to an existing flow| BD["Bounded"]
  C -->|New project, subsystem, or interface| AR["Architectural"]
  S --> S1["Approve the question and probe"] --> S2["Report a recommendation"]
  BD --> B1["Short design in chat"] --> B2{"Approved?"} -->|yes| B3["Implement with TDD"]
  AR --> A1["Questions, approaches, design sections"] --> A2["Write spec.md"] --> A3{"Spec approved?"} -->|yes| A4["writing-plans writes plan.md"] --> A5["Implement"]

An approval covers the stage it was given for. Approving an idea does not approve a spec that does not exist yet, and approving a spike does not approve the change that follows it.

The artifact chain

The feature playbook runs this chain as steps. Each stage commits a file that the next stage reads. When the repository has a docs/features/ folder, every feature gets its own folder there, docs/features/<slug>/, holding spec.md, plan.md, and review.md.

flowchart LR
  SP["spec.md: brainstorming"] --> PL["plan.md: writing-plans"] --> IM["Implementation: TDD and subagents"] --> RV["review.md: finishing-a-development-branch"] --> M["Merge"]

Artifacts are edited in place when a feature changes, and git is the history. To see how a spec changed, run git log -- docs/features/<slug>/. Without a docs/features/ folder, the agent writes specs and plans under docs/text2prod/ and writes no review.md.

Prototype before you pick

When the open question is which layout, interaction, or behavior to build, run the prototype playbook. It is the spike path with more than one variant. The agent builds throwaway versions in a scratch directory, puts them behind one switcher with each variant labeled, and shows you the result on the surface you use. For a visual choice that means a screenshot of each.

/text2prod:zed-mode use the prototype playbook. prototype two layouts for the settings page behind a toggle and send me a screenshot of each before we pick.

You get alternatives, trade-offs, and a recommendation. The prototype code stays throwaway, and the real build follows through the feature playbook.

Turn a settled design into a plan

Once you approve the spec, the writing-plans skill writes plan.md beside it. It maps which files change first, then splits the work into small tasks. Each task carries its own test, and each step inside a task is one action of two to five minutes: write the failing test, run it, write the code, run it again, commit.

/text2prod:zed-mode turn the approved spec into a plan of small tasks, each with its own test.

When the plan is saved, the agent offers two ways to run it, covered in chapter 5. For work that spans phases or stacked PRs, use the multi-phase-plan playbook. It writes a plan with one section per phase, and one phase is one PR with its own evidence. It stops after the plan and waits for your go.

Challenge a contested design

When two people disagree, or a change is risky, the interrogate skill sends at least two reviewers at it, each leading with a different angle. The lead then checks every finding against the code. The skill never applies a change. It sorts the findings into Act on, Consider, Noted, and Dismissed, and you decide what to act on.

/text2prod:zed-mode interrogate this design. read-only. report only real risks, not style.
