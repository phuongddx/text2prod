Guide Playbooks

Build and clean

Build in small steps that each get verified, hand tasks to fresh subagents when they are independent, and keep the prose the agent writes plain. This chapter covers the skills that do that and the playbook for each kind of change.

Tests first

The test-driven-development skill has one rule: no production code without a failing test first. The cycle has three steps.

  • Red: write one minimal test for one behavior, run it, and confirm it fails for the right reason.
  • Green: write the simplest code that passes, run the tests, and confirm the others still pass.
  • Refactor: clean up only after green, and add no behavior.

If the agent wrote code before the test, the skill says to delete the code and start over. A test that passes on the first run proves nothing, because it never showed it can catch the bug.

/text2prod:zed-mode use the feature playbook. add a --dry-run flag to the bump script. it prints what would change and writes nothing. tests first.

Run a plan

Once a plan exists, there are two ways to run it. subagent-driven-development dispatches a fresh subagent for each task and runs a task review (spec compliance and code quality) after each one, then a broad review of the whole branch at the end. It does not pause between tasks. It stops only for an irreversible or destructive operation, a security-sensitive action, a side effect outside the worktree (a merge, a push to a shared branch, a publish), or a plan too broken to follow. executing-plans runs the plan in batches with review checkpoints. The skill itself says to prefer the subagent route when your harness can dispatch subagents.

The subagent route picks a model for each role. It uses the least powerful model that can do the job: a fast model for mechanical tasks of one or two files, a standard model for work that spans files, and the most capable model for design work and the final whole-branch review. It sets the model explicitly on every dispatch, because an omitted model inherits the session's.

The dispatching-parallel-agents skill applies when you have two or more independent problems, such as test files failing for unrelated reasons. It sends one agent per problem, all in the same message so they run at once. It does not apply when the failures are related or when the agents would touch the same state.

The using-git-worktrees skill gives the work an isolated workspace. It first checks whether you are already in one, then uses the harness's native worktree tool, and falls back to git worktree only when there is no such tool. It asks before creating a worktree unless you have already stated a preference. Both execution skills start by ensuring isolation, and neither starts implementation on main or master without your consent.

Pick the playbook for the change

Name the playbook that matches the change. Each one ends with its own proof.

PlaybookUse it whenWhat it ends with
bug-fixA reported defect needs to be reproduced, root-caused, and fixed.A failing repro committed before the fix, then the failing and passing repro output pasted verbatim.
refactoringThe structure changes and the behavior does not.A test pinned before any move, and proof on the real artifact that behavior is unchanged, such as a script that diffs old and new output. If the change does not make the code easier to read, it is reverted.
perf-issueSomething is measurably slow.A baseline number and a post-fix number from the same tool and inputs, reported as one primary number with its unit, before and after.
hillclimbOne metric needs to improve toward a target over many iterations.A frozen measurement harness, one change per iteration kept or reverted, a decision log, and the metric from baseline to final with its percent change.
visual-parityTwo UIs must match pixel for pixel.An image diff of zero against the baseline for each component. A nonzero diff is a fail.

Clean the prose

The unslop skill cuts the patterns that make agent writing read as machine writing: filler such as "in order to" and "it is important to note", words like "crucial" and "pivotal", "not just X, but Y" constructions , em dashes, chatbot openers such as "I hope this helps", and flattery. It also replaces abstract nouns and vague claims with the concrete thing or number.

It applies to the agent's replies, docs, commit messages, PR bodies, code comments, review notes, and decision-log rows. A style you set in your own output style or instruction files overrides the rule it contradicts.
